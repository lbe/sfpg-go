# Spec: server wiring and everything else

Scope: how the app constructs, starts, stops and restarts the image-stack subsystems; handlers, dashboard, config; every changed file not owned by the discovery, thumbnail, metadata or storage components.
Sources: `git diff dev..refactorv2/image-stack` ("v2", "dev"). Line numbers are v2 line numbers unless marked `dev:`. Evidence means I read the diff or code; inference is marked.

## 1. Behavior

### 1.1 Startup sequence (`App.Run`, `internal/server/app_startup.go`)

Dev order and v2 order differ in two places only (a, b).

1. `setupBootstrapLogging`, scheduler start, profiler (unchanged from dev).
2. `app.setDB()` creates the pools. v2 additionally builds `database.NewPoolOwner` and `database.NewComponent` (`infrastructure_pool.go:51-80`). No write batcher, discovery service, file processor or discovery queue exists yet. `TestV2APP_ProductionDiscoveryAcceptance` (`v2_app_integration_test.go:26`) asserts this ("writer or discovery assembled before effective configuration reconciliation").
3. `setConfigDefaults`, then `loadConfig` or restore-last-known-good, then `reconfigurePoolsFromConfig` (unchanged order from dev).
4. `rssmonitor.Run`, then `StartWriteBatcher(ctx, deferDQueDrain=true, dqueMaxDiskBytes)` (`app_startup.go` ~L205). The dque drain is deferred until the server is listening (`onServerListening` calls `StartDQueDrain`, which now calls `dbComponent.StartDQueDrain`, `infrastructure_pool.go:137`).
5. `ApplyConfig`, `ensureHTTPCacheKeyFormatCurrent`, `initializeHTTPCache`.
6. `app.Start` = `SubsystemManager.Start` (`subsystem_manager.go:80`). It panics with `"main"` if `infra.dbComponent == nil` (L91-93). It builds the discovery backlog queue, the file processor, the worker settings and the `discovery.Service` (see 1.3).
7. Startup discovery decision (unchanged): `run_file_discovery` config, overridden by env `SEPG_SKIP_STARTUP_DISCOVERY` (config-restart re-exec). Stats hydrate only when discovery does not run (`HydrateFileProcessingStats` now calls `discovery.Service.Hydrate`).
8. **Change (a):** worker pool start (`app.StartPool`) moved from after the discovery goroutine to before it (`app_startup.go` diff hunk at "Worker pool startup"). Dev started the discovery goroutine first. Needed because `Run` in `discovery.Service` calls `StartWorkers(nil,nil)` itself; inference: the reorder is not required by that. Not observable externally.
9. Discovery goroutine (unchanged semantics): `TriggerDiscovery(context.Background())`; `files.ErrFolderIndexRebuild` -> log `"startup folder-index rebuild failed; shutting down"` + `app.Shutdown()`; other error -> return; else if `RestartAfterDiscovery` -> log `"discovery complete; requesting process restart"` (`reason=discovery-complete`) + `TriggerRestart()`.
10. Completion monitor (unchanged poll logic): waits up to 30 s, 100 ms tick, for `qSendersActive>0 || TotalFound>0`, then `waitForFileProcessingDrain`, then logs `"File processing completed"` (`found`, `existing`, `inserted`, `skipped_invalid`) and schedules pragma optimize. Operators/tests depend on this line (`app_startup.go:360`).
11. **Change (b):** `waitForFileProcessingDrain` (L90-96) no longer polls four counters every 100 ms. It returns nil when `q`, `processingStats` or `fileProcessor` is nil, else `discovery.Service.Wait(ctx)`. No timeout; `ctx` is `app.getCtx()` (shutdown cancels).

### 1.2 TriggerDiscovery (`server.go:392-420`)

- Dev: `App.discoveryRunning` CAS guard, `ResetStats`, `GalleryStats.markRunning(+1/-1)`, `module_state.SetActive(true/false)` (false with `context.Background()`), seam check, refuse when queue/senders non-empty, `files.WalkImageDir`, drain, `WalkPathStore.Reset`, persist stats, rebuild `file_folder_index`. Log `"discovery already in flight"` (Info) on a lost CAS; returned nil.
- v2: `TriggerDiscovery` ignores its `ctx` (`_ = ctx`, L393) and calls `SubsystemManager.ensureDiscovery(app.getCtx(), imagesDir, normalizedImagesDir).Run(app.getCtx())`. All steps above moved into `discovery.Service.Run` (`internal/discovery/service.go:154-254`). Hooks wired in `configureDiscoveryAdapter` (L398-420): `discoveryOverride` (the `testSeams.TriggerDiscovery` seam), `discoveryOnActivity` (`GalleryStats.markRunning`), `discoveryOnFileInserted` (`GalleryStats.addFile`), `discoveryFinalize` (nil RW pool: log `"cannot rebuild file_folder_index: RW pool is nil"`, return nil; seam `RebuildFileFolderIndex`; nil component: `files.ErrFolderIndexRebuild`; else `dbComponent.FinalizeIndex`).
- Behavior kept: concurrent trigger returns nil (`service.go:161-163`); refuse message `"discovery walk refused: queue backlog or active senders must be empty before walk"` (`service.go:219`); stats persisted after drain, persist failure logged not fatal; cancel during run returns the context error; rebuild failure returned (wrapped by the storage component as `ErrFolderIndexRebuild`, unverified in this component).
- Behavior lost: the Info log `"discovery already in flight"` no longer exists (`git grep` finds none in v2). Dev tests may have relied on it; decision in section 6.
- New: caller cancellation never cancels an admitted run (`TestTriggerDiscovery_CallerCancellationDoesNotCancelAdmittedRun`). In dev the walk already used `app.getCtx()`; only the seam received the caller ctx. Observable change is minimal.

### 1.3 SubsystemManager.Start (`subsystem_manager.go:80-196`)

- Re-entrant: closes any prior `discovery.Service`, closes an owned file processor, resets `shutdownOnce` (L94-108).
- `moduleStateService = modulestate.NewServiceWithBackend(dbComponent.ModuleState())` (dev: `NewService(DBRwPool())`).
- Discovery backlog: `dbComponent.ResetDiscoveryBacklogAt(ctx, discoveryDQueDir)` replaces dev's `os.RemoveAll(dir)` + `newDiscoveryDQueAdapter`. Directory is `<dir of main db>/discovery-dque` (`infrastructure_pool.go:70-73`). Queue is wiped on every start (a full re-walk is recovery). Failure: log + `panic("main")`.
- Default file processor: `files.NewFileProcessorWithDiscoveryStorage(dbComponent, imagesDir, dbComponent.PendingWriteCount)`, `ownsFileProcessor=true`. Tests may inject a processor, which is then "borrowed" and closed only at final Shutdown.
- Worker count (new): config positive values override `App.Run` args (dev behavior); `maxWorkers==0 -> workerpool.DefaultMaxWorkers()`; then `maxWorkers = memlimit.Apply(maxWorkers, metadata.PoolSize())` (L179-183). Idle time default 10 s, config `WorkerPoolMaxIdleTime`. memlimit rules (commit 35233fa message): GOMEMLIMIT honored if set; else soft limit from worker count and ExifTool pool size, capped at 75 % of total RAM (lower of MemTotal and cgroup `memory.max`); one `"memory limit"` log line per start; workers drop to 1 if one does not fit. Owned by the memlimit component; this wiring is the only production caller of `memlimit.Apply` (git grep).
- ExifTool pool size `min(4, max(2, NumCPU/3))` (commit message, metadata component).
- Pool is created inside `discovery.New` via `ensureDiscovery`; `m.pool = discovery.WorkerPool()`.

### 1.4 Shutdown ordering (`app_lifecycle.go:26-66`, `subsystem_manager.go:217-235`, `infrastructure_service.go:143-180`)

Order, identical to dev except step 3 and the internals of 4, 5 and 7:

1. `LogProfileLocation`; cancel `RuntimeManager` ctx.
2. Wait `poolDone`, then `RuntimeManager.wg`.
3. Poll every 100 ms until `SubsystemManager.discoverySnapshot().Active` is false (dev: `discoveryRunning.Load()`). Guarantees pools are not closed while a run is in its drain/rebuild phase (test: `app_shutdown_test.go`, "database pools reached closure before discovery joined").
4. `SubsystemManager.Shutdown` (once, `sync.Once`): preload manager shutdown, `discovery.Close()`, close file processor if borrowed or no discovery exists, `dbComponent.CloseDiscoveryBacklog()` (else `q.Close()`). Dev: preload, `fileProcessor.Close()`, `q.Close()`. Order preload -> processor is asserted by `TestV2METABorrowedProcessorInitAndFinalClose`.
5. `shutdownWriteBatcher`: **new** sets `cacheWritesClosed=true` under `cacheWriteMu` write lock so in-flight `submitCacheWrite` calls finish and later ones return the entry to the pool and drop it (`infrastructure_cache.go:104-110`, `infrastructure_service.go:143-148`). Then `dbComponent.CloseWriteBatcher()` (dev: `writeBatcher.Close()`).
6. `runShutdownPragmaOptimize` with a 30 s timeout (unchanged).
7. `closeDatabasePools` via `dbComponent.ClosePools()` (dev: close RW then RO pools).
8. Logger shutdown.

### 1.5 ReconfigurePools (`infrastructure_pool.go:147-213`)

Dev: compare old and new limits, recreate pools, rebuild cache store, close and recreate the write batcher with `1000`, `200 ms`. v2: delegates to `dbComponent.Reconfigure(ctx, cfg, recreateFn, cfg.DQueMaxDiskBytes)` which returns `(changed, err)`. If not changed, returns the error or nil. If changed with an error, logs `"failed to recreate write batcher"` and continues. Then logs `"reconfiguring database pools from loaded config"` with `old_max,new_max,old_min_idle,new_min_idle` plus **new** `old_monitor_interval,new_monitor_interval`. Then rebuilds `cacheStore`, calls `cacheMW.UpdatePool`. The ordering of the log line moved after the reconfigure (dev logged before recreating). Tests `TestReconfigurePools_LargeDQue_DoesNotBlock`, `TestShutdown_LargeDQue_DoesNotBlock` assert neither blocks on a large dque.

### 1.6 Write batcher and WAL (`infrastructure_batcher.go`)

Batcher construction (limits `MaxBatchBytes 8 MiB`, `ChannelSize 4096`, `DQueItemsPerSegment 250`, `MaintenanceInterval 5 min`, initial `10000`/`50 ms`, after reconfigure `1000`/`200 ms`) moved out of the server package into `database/storage` (storage component; not re-verified here). The server only passes `storage.WriterHooks` (cache size/count atomics, `OnFolderCreated`, evict, resync, optimize interval, `lastFlushWroteDML` sync, test flush override) and `storage.StoreTestSeams`.
`walCheckpointAfterCommit` now delegates to `storage.WalCheckpointAfterCommit`. Constants preserved in dev source: WAL size threshold 256 MiB, 5 min interval, skip while rebuild scan cursor held, skip post-flush when no DML. I did not re-read the storage copy; owner of storage must confirm they are intact.

### 1.7 Config and flags

- `DefaultConfig().DBMinIdleConnections`: 10 -> 1 (`config.go:178`). UI placeholder `"10"` -> `"1"` (`config-performance-tab.html.tmpl:187`). `SetupDB` now reads both defaults from `config.DefaultConfig()` instead of literals 100/10.
- `DefaultConfig().RestartAfterDiscovery`: false -> true (`config.go:192`). Effect: after startup discovery the process re-execs itself (`TriggerRestart`, `ExecRestart` with `SEPG_SKIP_STARTUP_DISCOVERY=1`) so RSS from image-decode churn is returned. Docs: `ENV_CONFIGURATION.md`. Applies only to startup discovery, not `POST /server/discovery`.
- Both from commit 35233fa. Neither is on the approved list. See 2.
- No new config keys or flags. Precedence unchanged. `getopt` error text changed: `"session secret is required: set SEPG_SESSION_SECRET"` (already carried to v3 as 3108e79).
- New on-disk: `discovery-dque/` next to main db (existed in dev too under another path; the dev path is `discoveryDQueDir` computed in `Start`, same value; no change observed). `sfpg.db-dque/` unchanged (`infrastructure_pool.go:66-69`).

The rebuild reads chunks and resumes after the last complete folder, bounding memory. Result rows unchanged.

## 5. Boundary notes (`go list` on the v2 checkout)

- `internal/server` imports (new for v2 in bold): `discovery`, `memlimit`, `metadata`, `parallelwalkdir`, `server/database`, `server/database/storage`, plus all dev imports. It is the composition root. It imports `metadata` and `memlimit` only to call `metadata.PoolSize()` and `memlimit.Apply` for worker sizing (`subsystem_manager.go:183`) and `parallelwalkdir` for a type used in `ensureDiscovery`. Proposal: let `discovery.New` take `MaxWorkers` plus the loader and compute the memory clamp inside the discovery or memlimit owner (R17) so `server` imports neither `metadata` nor `parallelwalkdir`.
- `internal/server/files` is imported by `server/database` and `database/storage`, and `gallerylib` is imported by `server`, `database`, `database/storage`, `files`: acyclic and fine. `files` imports `metrics`; `modulestate` imports `metrics` and `database/storage` and `storagepayload`. Evidence: `go list`. The `modulestate -> database/storage` edge means `modulestate` is partly a storage detail; inference: its new `NewServiceWithBackend` exists to break the cycle `storage -> modulestate -> storage` (R11). Needs the owner of storage/modulestate to confirm. Proposal: move module-state persistence into `database` and delete the backend indirection.
- `internal/server/interfaces`: imports `config`, `session`, `dbconnpool`, `gallerydb`; imported by `server`, `handlers`, `cachepreload`. It exists to break the `server <-> handlers` cycle (R11, dev-existing, not changed in v2). Leave; no v3 action.
- `internal/server/handlerqueriesfake`: imported by no package (only its own tests; test fixture). Dev-existing. R5/R9 concern is not new. Leave.
- `internal/server/metrics` imports `cachebatch`, `cachepreload`, `workerpool`, `writebatcher`. Imported by `server`, `files`, `handlers`, `modulestate`, `ui`. In v2 `files.ProcessingStats` is adapted at the server edge (`discoveryMetricsAdapter`), meaning `metrics` should not know `FileProcessingMetrics` field-for-field; fine.
- `InfrastructureService` + `SubsystemManager` + `App`: ownership of the write batcher and discovery is split between these three and `database.Component`/`discovery.Service`. Proposal: v3 `App` holds one `*database.Component` and one `*discovery.Service`; delete `InfrastructureService` fields `dbOwner`, `dbRwPool`, `dbRoPool`, `writeBatcher`, `folderIndex` and the sync helpers. Requires approval if any exported type is removed (R2).
