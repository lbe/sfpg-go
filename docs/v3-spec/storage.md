# Spec: STORAGE AND DATABASE (v2 = refactorv2/image-stack, base = dev)

Evidence tags: `[v2]` read from the v2 checkout, `[dev]` read with `git show dev:`, `[tool]` output of `go list` / `deadcode . ./cmd/sfpg-go-dashboard` run on the v2 checkout, `[inference]` my reading. Line numbers are per file.

Headline findings:

1. Most of the write path (batch envelope, flush, folder-index protocol, submit retry, WAL/optimize maintenance, cache ops, module-state SQL) already existed in dev in `internal/server` and `internal/cachelite`/`modulestate`. v2 MOVED it into a new `internal/server/database/storage` package and left alias/wrapper shells behind. The observable behavior change in this component is small (section 1.B). The rest is relocation plus test seams.
2. `internal/storagepayload` exists only to break import cycles (R11). Section 5 shows the cycle and the ownership problem it hides.
3. v2 copies the thumbnail three times per file on submit (R25). dev copied it zero times.
4. A large amount of v2 production code is reachable only from tests (R5): section 4.

## 1. Behavior

### 1.A Behavior dev already had (relocated by v2, same values)

**Unified write batcher** (`writebatcher.New` config). dev: `server/infrastructure_batcher.go:27-36,113` [dev]. v2: `storage/writer.go:73-182` [v2].

- `MaxBatchSize`: 10000 at startup with `FlushInterval` 50ms (`writer.go:20-34`, called with `deferDQueDrain` from `app_startup.go:222`, `app_cli.go:98` passes false). After a pool reconfigure the batcher is closed and rebuilt with 1000 / 200ms and `deferDQueDrain=false` (`writer.go:36-49`; dev `infrastructure_pool.go:160`).
- `MaxBatchBytes` = `int64(8 * 1024 * 1024)` (`writer.go:80`). In-flight bytes per item come from `BatchedWrite.Size()` (`batched_write.go:97-120`): file = `Thumbnail.Cap() + 512` (512 if no thumbnail); cache entry = `len(Body) + 256`; folder-index row = 128; other = 64.
- `ChannelSize` 4096 (`writer.go:82`), `DQueItemsPerSegment` 250 (`:84`), `MaxDiskBytes` = config `DQueMaxDiskBytes` (default `DefaultDQueMaxDiskBytes = 50 << 30`, `config/config.go:142`; hot-reloaded by `SetMaxDiskBytes`, `app.go:324-327`), `MaintenanceInterval` 5 min (`:180`).
- Write-overflow dque dir: `<mainDBPath>-dque` (`component.go:45-48`, `:60-66`); dque name `"writebatcher"`, `dque.NewOrOpen` + `TurboOn` (`writebatcher/dque.go:62-67`).
- Queue item gob format: `BatchedWrite` = three `[]byte` blobs (File, CacheEntry, FolderIndex), each a gob of the payload (`batched_write.go:23-84`); `File` has custom `GobEncode` that turns `*bytes.Buffer` into `[]byte` (`storagepayload/file_gob.go:40-87`). Same as dev `server/batched_write.go` [dev].
- Per-flush flow (`writer.go:197-273`; dev `server/batched_write_flush.go`): split batch into files / gallery cache (`Path` prefix `/gallery/`) / other cache; `PrepareFolderIndexFlush`; one `gallerylib.Importer` per batch; files first, then gallery cache, then other cache, then `InsertFileFolderIndexNewRows`; one transaction per batch obtained from the RW pool in `BeginTx` and returned in `OnSuccess`/`OnError` (`writer.go:90-104,116-122,150-157`).
- `OnSuccess` (`writer.go:116-149`): adds cache bytes/entries to `CacheSizeBytes`/`CacheEntryCount`, calls `EvictCacheAfterBatch`, `OnFolderIndexBatchSuccess`, fires `OnFolderCreated` once per folder created in the batch, releases pooled buffers.
- `OnError` (`writer.go:150-178`): returns conn, logs `slog.Error("failed to flush unified batch", err, files, cache_entries, folder_index)`, and if any cache entry was in the batch runs `ResyncCacheSize` with a 3s timeout.
- `DropWithoutFlush` = `ShouldDropIndexOnlyBatch`: a batch that is only folder-index rows while no rebuild is active is dropped before `BeginTx`, logged `slog.Info("writebatcher: dropping folder-index batch before BeginTx", count, reason="rebuild inactive")` (`folder_index_protocol.go:156-163`).
- Post-commit maintenance (`writer.go:179`, `maintenance.go:20-79`, `writer.go:289-323`): WAL `PRAGMA wal_checkpoint(TRUNCATE)` when the `-wal` file is > 256 MiB (`maintenance.go:36`) or >= 5 min since last checkpoint (`:48`); skipped while the rebuild RO cursor is open (`rebuildScanHeld`) and on post-flush calls where the last flush wrote no DML. `PRAGMA optimize` (`dbconnpool.PragmaOptimizeDefault`) when the interval (`DBOptimizeIntervalNanos`, default 1h) has elapsed since `LastPragmaOptimizeRun`; no run when `lastRun` is zero.
- Folder-index submit (`index_batcher.go:82-130`; dev `server/batcher_wiring.go`): `inflightAdd(1)` then `Submit`; on `ErrFull`/`ErrQuotaExceeded` polls every 100ms (`time.Sleep`) and resubmits when `PendingCount` falls; gives up when pending has not fallen for 30s (`submitStallDefault`, `:12`). `ErrClosed` returns immediately. File submit logs `slog.Warn("unified batcher full, dropping file write", path, pending)` on `ErrFull`.
- Generation: `bumpGeneration` = `time.Now().UnixNano()` (or prev+1 if 0/equal) so stale dque rows from a prior process are skipped (`folder_index_protocol.go:74-85`, skipped rows logged `slog.Error("skipping stale folder index write")`). Rows are skipped with `slog.Error` when rebuild is inactive or `file_folder_index_new` is missing (`:195-207`).
- Per-file write (`file.go:132-214`; dev `files/thumbnail.go`): `UpsertPathChain`, delete stale `invalid_files` row (warn on failure), metadata replace, thumbnail upsert only if needed (existence query only when the file pre-existed, determined by `updated_at > created_at`), folder-tile update once per dir per batch (failure is logged, non-fatal). Thumbnail row: `size_label "m"`, `format "jpg"`, height/width 0, `created_at = updated_at = now` (`file.go:71-80`).
- HTTP cache storage (`cache.go`, `cache_body.go`; dev `cachelite/cache.go`, `body_storage.go`): get decodes the body with `bodycodec` using `content_length` as the uncompressed length; store runs `FinalizeForStorage` (compress in place unless magic already matches); write codec default `"zstd-1"`, `"identity"` skips the registry; `EvictLRU` reads 1000 oldest rows and deletes until `targetFreeBytes` reached, summing `StoredLength`; `CleanupExpired` returns the constant `1` (`cache.go:247`; same in dev `cachelite/cache.go:312`); `RotateCacheTable` = `tableswap.CloneEmpty` + `CreateIndexes` + `Swap` of `http_cache`.
- Module state (`module_state.go`; dev `modulestate/service.go`): table `module_state`; `SetActive` stamps `last_started_at` (active) or `last_finished_at` (inactive) with `time.Now().Unix()`; payload JSON key `"file_processing"` with `total_found, already_existing, newly_inserted, skipped_invalid`; a corrupt payload on save is replaced by an empty doc; on load it is an error; unknown row = inactive / zero.
- Table swap (`tableswap`): unchanged code. `CreateIndexes` sets `temp_store=FILE` for the call (comment-only diff in v2, behavior was in dev) [v2 diff].
- Pool (`dbconnpool`): unchanged defaults. RW conn recycled after `rwRecyclePutCount = 100` puts or SQLite memory > `rwRecycleMemBytes = 10 MiB` (`dbconnpool.go:121-122`, in dev). Pool limits `EffectivePoolLimits(cfg)`; config default 100/1/1m (comment-only change).

### 1.B Behavior that is new in v2

1. **Folder-index rebuild in folder-bounded chunks** (`storage/folder_index.go:54-139,147-229`; SQL `sqlc/queries/file_folder_index_rebuild.sql`). dev read all `(file_id, folder_id)` pairs into one slice pre-sized by `COUNT(*)`. v2:
   - query `... WHERE folder_id IS NOT NULL AND folder_id > ? ORDER BY folder_id, filename, id`; first call uses `after = math.MinInt64` (`folder_index.go:95`).
   - Chunk = at least `rebuildChunkPairs = 1 << 18` (262144) pairs, ending at the first row of a new folder (`:177-180`); a folder is never split; a folder larger than the chunk is read whole. `COUNT` query and `CountFilesForFolderIndexRebuild` are deleted.
   - Per chunk: RO conn Get, query, set `scanHeld(true)`, read, `rows.Close()`, `scanHeld(false)`, RO conn Put, all before any Submit (`:147-195`). Next chunk resumes at `after = last folder_id written`.
   - Pairs buffer allocated once, `make([][2]int64, 0, 1<<18)` = 4 MiB, reused with `pairs[:0]` (`:94,102`).
   - Cancellation returns the bare `ctx.Err()`; every other failure wraps `ErrFolderIndexRebuild` (`:22,62-65,303`). After the last chunk: wait for `inflight == 0` (poll 100ms, fail if unchanged for 30s, `:265-294`), then `CreateIndexes` and `Swap` on a fresh RW conn. RW conn is released right after `CloneEmpty`.
   - Logs (debug): `file_folder_index_new population starting|completed successfully|failed` with `elapsed`.
2. **Retry-safe payload lifetime.** dev's `WriteFileInTx` returned the thumbnail buffer to the pool after the SQL succeeded but before commit, so a commit failure re-enqueued items whose thumbnails were gone. v2 `WriteFileAttemptInTx` (`file.go:123-130`) works on a copy and the batch releases pooled buffers only in `OnSuccess` or, for items `reEnqueueBatch` could not resubmit, in the new `writebatcher.OnRelease` (`writebatcher/flush.go:108-124`, `batcher.go:131`). Metadata is written by replace (delete then insert; new queries `DeleteExif`, `DeleteIPTCKeywordsByFile`, `InsertIPTCKeywordForFile`, `DeleteXMPPropertiesByFile`, `InsertXMPPropertyForFile`) so a retried file is idempotent. (Metadata persistence is covered by the metadata spec; listed here because it shapes the batch contract.)
3. **Processed-file submission.** `Store.SubmitProcessed(ProcessedFile)` (`processed.go:105-120`) replaces `UnifiedBatcher.SubmitFile(*File)` as the processor entry point. It clones the snapshot, maps it to the legacy `storagepayload.File`, and enqueues `BatchedWrite{File: wire}`; on submit failure it returns the thumbnail to the pool. Returns `writebatcher.ErrClosed` when no batcher.
4. **Invalid-file recording owned by storage.** `RecordInvalid` resolves the parent folder via `GetFolderIDByPath(parentDir)`; error `no folder for gallery path parent %q` when missing; upserts `invalid_files(path, mtime, size, reason, folder_id)` (`processed.go:130-175`). `reason` empty -> NULL.
5. **Hash cutover** (`database/hash_cutover.go`, migration `024_clear_legacy_phash`: `UPDATE files SET phash = NULL WHERE phash IS NOT NULL`). On `Setup`, `migrateMainWithCutover` reads `schema_migrations` strictly (exactly one row, integer version >= 0, integer dirty 0/1, not dirty, else error) and, when there is no row or `version < 24`, removes `<mainDB>-dque` (`os.RemoveAll`) before `m.Up()`. Purpose: queued dev-format items carry old phash values. `migrateDB` now opens driver `"sqlite"` instead of `"sqlite3"` (`app.go`, diff). Result of this section: any dque content written by dev is discarded on first v2 start, so the pre-DB02 gob compatibility fixtures only matter if v2 itself shipped.
6. **Writer lifecycle:** `Component.Reconfigure` recreates pools, re-points the store and module-state store, and rebuilds the batcher only if one was running (`component.go:156-183`); on recreate error both pools are closed and cleared (`pool_owner.go:62-97`). `PoolOwner.Close` closes RW then RO, first non-`ErrPoolClosed` error wins, handles cleared.
7. **dbconnpool:** `Close` now joins the monitor goroutine (`monitorWG`, `dbconnpool.go` diff `p.monitorWG.Go(p.monitor)`, `Wait()` after `close(p.done)`); monitor body extracted to `monitorTick`. Doc fix: `HealthCheckThreshold` zero means default 30s, negative means ping every Get. No other behavior change.
8. **Chunk-related SQL API change:** `CustomQueries.QueryFilesForFolderIndexRebuild(ctx, afterFolderID int64)`; `CountFilesForFolderIndexRebuild` and its prepared statement removed. `PrepareCustomQueries` no longer pretends to ATTACH thumbs (comment/placeholder change only).
9. **Drain/wait:** `Store.WaitWrites` polls `PendingCount()==0` every 100ms honoring ctx (`discovery.go:170-186`); `Store.FinalizeIndex` runs the rebuild with the store's pools and writer (`drain.go`). New capability for the discovery component (out of my scope to judge).

### 1.D Lifecycle and ownership (v2)

- `Component` owns `PoolOwner` (paths + RW/RO pools), `Store`, module-state store. `Store` owns the batcher, protocol atomics, discovery backlog handle, last-flush flag. The batcher worker goroutine is owned by `writebatcher` (stops on `Close`; Close does not drain the dque, items persist for next start, `writebatcher/batcher.go:40`). The DB conn for a flush is acquired in `BeginTx` and released in `OnSuccess`/`OnError` via variables captured by closures (`writer.go:74-76,98,117-121`).
- Production callers of `Component`: `infrastructure_pool.go:68,155,182`, `subsystem_manager.go:110,131`. `database.Open` has no production caller [tool: unreachable `component.go:39`].

## 2. Approved changes versus other changes

Approved (R4) and where they touch this component:

- **New pHash:** `files.phash` is nullable `int64`; migration 024 nulls old values and `hash_cutover.go:45` discards the dque so no old-format hashes survive. `ProcessedFile.Phash NullInt64`, `File.File.Phash`. Storage writes it through `UpsertPathChain(..., phash, ...)` unchanged.
- **Wuffs decode:** none in storage. The only coupling is the `thumbnail` import for pooled buffers (`batched_write.go:122-135`).
- **ExifTool metadata / IPTC:** the batch carries `Exif`, `Itpc`, `XmpProps`, `XmpRaw` as before; persistence changed to replace-by-file queries (1.B.2). Keywords are `IPTCKeywords` rows, written by `InsertIPTCKeywordForFile` (covered by the metadata spec).
- **Malformed JPEG fails in decode:** not in this component. Side effect: `File.HasValidJpegMarkers` is removed from `File`.

Unapproved change: needs a decision

1. **Folder-index rebuild is chunked** (1.B.1). Memory and query shape change; output rows are intended to be identical. Recommend keeping: bounded memory is the point of the user's `file_folder_index` work (file `sqlc/queries/file_folder_index_rebuild.sql` change). Ask the user to confirm it is wanted behavior (it is listed in my brief as in-scope behavior).
2. **Hash cutover discards `<db>-dque`** on upgrade from schema version < 24 (1.B.5). Data loss of queued overflow writes is intended but not in the approved list. Recommend keeping, minus the injected `removeDirectory` parameter (plain `os.RemoveAll`).
3. **Strict `schema_migrations` validation** (multiple rows, typeof checks) in `migrateMainWithCutover` (`hash_cutover.go:12-43`): new failure modes for a corrupted version table. Recommend dropping the typeof/multi-row checks and using `m.Version()` from golang-migrate (R7).
4. **`sql.Open("sqlite", ...)` instead of `"sqlite3"`** in `migrateDB` (`app.go` diff). Cause unknown to me; no comment explains it. Needs the user to say why.
5. **dbconnpool `Close` joins the monitor goroutine** (1.B.7): behavior change at shutdown (Close can now wait for an in-progress tick). Recommend keeping; it satisfies R18.
6. **Thumbnail triple copy on submit** (section 4, `processed.go`): performance regression, not intended behavior (R25).
7. **Retry-safe release (`OnRelease`)** (1.B.2) is a bug fix, not requested. Recommend keeping the semantics, with fewer layers (see 4).
8. **`CleanupExpired` returning constant 1** is a dev bug that v2 preserved (`cache.go:247`); app logs "deleted" from it (`app_startup.go:401`). Needs a decision: fix (return `RowsAffected`) or keep.

**`storagepayload` is a cycle breaker (R11), evidence-based.** Why it exists: v2 puts `BatchedWrite` and all cache DB ops in `storage`. `BatchedWrite.CacheEntry` needs `HTTPCacheEntry`, and `cachelite` wants to delegate to `storage`, so `storage` cannot import `cachelite`; the type is parked in a third package. Same for `File` (needed by `files`, `discovery` and `storage`: `files` imports `discovery` imports ... and `storage` imports `files`' type), `DiscoveryPathWork` (`discovery` and `storage`), `FolderIndexRow` (`files`, `storage`), `FileProcessingRunState` (`modulestate`, `discovery`, `storage`). The package's own header says so: "value types that move between discovery, the write batcher and the database layer" (`storagepayload/file.go:1-4`). Hidden ownership problems:

1. `cachelite` imports `storage` (inverted): the cache package should own `HTTPCacheEntry` and its DB operations (dev layout). `storage` needs `cachelite` only for the cache-entry arm of `BatchedWrite`, and `cachelite` imports neither `files` nor `server`, so `storage -> cachelite` is acyclic once the wrappers are gone.
2. `File` is the processor's output type; its owner is `files` (as in dev). `storage` needing it is a consequence of putting the writer below `files`. In dev the writer lived in `server`, above both, and `files` declared its own `UnifiedBatcher` interface (a valid R8 case: one consumer, many fakes).
3. `ProcessedFile` + `Null*` types exist to keep `sql.Null*` out of discovery (R16) but then get mapped straight back into `sql.Null*` (`processed.go:42-103`).

Proposals (all need user approval: R1, R2):

- **A (recommended, minimum change): keep dev's layout.** `BatchedWrite`, flush, `folderIndexProtocol`, `fileBatcher` stay in `internal/server`; `files.UnifiedBatcher` stays the consumer-owned interface; cache code and `HTTPCacheEntry` stay in `cachelite`; `modulestate` stays; `RebuildFileFolderIndex` stays in `files`, with chunking added in place. Net new packages 0, new exports 0 beyond `OnRelease` and the `afterFolderID` parameter. The v2 requirement for "database owns the write path" is then unmet, so ask the user whether it is a goal or only a v2 artifact.
- **B: if the database must own the write path, put it in the existing `internal/server/database` package, not a `storage` sub-package.** `database` imports `cachelite` (cache entry), `files` (File) and `thumbnail`; `files` must not import `database`. `files` keeps `UnifiedBatcher`/`SubmitFile(*File)`; `database` provides the implementation. `storagepayload` disappears: `HTTPCacheEntry` -> `cachelite`, `File` -> `files`, `FolderIndexRow` -> `database`, `DiscoveryPathWork` -> `discovery` (or `files` as in dev), `FileProcessingRunState` -> deleted, `Processed*` -> deleted. I did not verify v3's final `discovery`/`files` import structure; that is the discovery spec's decision.
- **Do not create** `storage`, `storagepayload` or `Component`/`PoolOwner` in v3 (R1, R11). Pool ownership stays on `InfrastructureService` as in dev (`infrastructure_pool.go` has `dbOwner`/`dbRwPool`/`dbRoPool` aliases already, a sign v2's owner was layered on top of a still-living original).
- `storage -> thumbnail` (a wasm-image package) only for `thumbnail.PutBytesBuffer` in the release path (`batched_write.go:124-135`); a `bytes.Buffer` pool owner belongs with the code that creates thumbnails; in Option A, `server` already imports `thumbnail`.
- `tableswap` and `writebatcher` are leaf utilities with a clear owner; keep.
