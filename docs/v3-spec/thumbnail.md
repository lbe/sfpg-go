# Spec: thumbnail and hashing

Scope: `internal/thumbnail`, `internal/memlimit`, `internal/server/files/thumbnail.go`, `internal/server/database/hash_cutover.go`, migration 024, `internal/gensyncpool`. Source: v2 = `refactorv2/image-stack` (cited as `path:line` on that branch). Rule IDs are from `docs/v3-review-rules.md`.

Method: read every file in scope, `git diff dev..v2`, `go list` and `deadcode . ./cmd/sfpg-go-dashboard` on the v2 checkout. Statements marked (inference) are not verified by running code. I did not run tests.

## 1. Behavior

### 1.1 Pipeline (called from `internal/server/files/processor.go:53-123`, per file)

1. `workspace.ReadSource(ctx, file, SizeBytes)` reads the whole file into worker-owned memory. `SizeBytes` comes from the walk and is only a hint (`processor.go:80`).
2. MIME is `http.DetectContentType` over the first 8192 bytes. Non-`image*` is skipped (processor, other component).
3. ExifTool reads the original path (other component), `image.DecodeConfig(bytes.NewReader(snapshot))` gives width/height (`processor.go:101`). It relies on the `image/gif`, `image/png`, `webp` blank imports in `thumbnail.go:14,16,21` (hidden coupling, inference: no other registration found).
4. `workspace.Generate(ctx, w, h)` decodes, makes the thumbnail, encodes JPEG, computes MD5 and pHash (`workspace.go:254`).
5. `ResetFile()` is deferred on every exit (`processor.go:55`).

Dev did the same with `thumbnail.GenerateThumbnailAndHashes(imageFile, w, h)` on an `io.ReadSeeker` (dev `processor.go:153`); the file was opened and read several times (stat check, marker check, decode, MD5). v2 reads once.

### 1.2 Decode (`workspace.go:254-333`)

Dispatch on `http.DetectContentType(snapshot[:min(len,8192)])` (`workspace.go:267-268`):

- `image/png` or `image/gif`: Wuffs (`decodeWuffs`, `wuffs_decode.go:56`). New in v2.
- Anything else, including JPEG and WebP: `fullImageDecodeHook` which defaults to `decodeFullImage` (`scaled_jpeg_decode.go:48`). JPEG (prefix FF D8 FF) is decoded with `m8rge/go-scaled-jpeg` at DCT scale `chooseJPEGDCTSize(srcW,srcH)` (`thumbnail.go:189`), clamp [1,8], ceil of fit-box/size, so the decoded JPEG covers the 200x150 fit box. Other formats go to `image.Decode` (WebP via `golang.org/x/image/webp`; unregistered formats such as BMP fail). No stdlib JPEG fallback: a JPEG scaled-decode error is the result (hard fail). Unchanged from dev (`scaled_jpeg_decode.go` differs only in a comment).
- In dev PNG/GIF went to stdlib `image.Decode`. GIF in v2 is frame 0 only, with its frame bounds (`wuffs_decode.go:155-183`). PNG is 8-bit premultiplied RGBA from Wuffs (`image-stack-v2-hash.md` "Accepted pixels"). (Whether dev stdlib GIF also gave frame 0 only: stdlib `image.Decode` for GIF returns the first frame, inference from Go stdlib behavior.)

Decode failures return `(nil, &NullString{}, &NullInt64{}, err)`; the processor logs and returns `generate thumbnail: %w` and the file is recorded invalid upstream (`processor.go:108-111`). Malformed JPEGs fail here since the marker pre-filter is removed (approved change).

### 1.3 Thumbnail, MD5, pHash (`workspace.go:309-333`, `thumbnail.go:245-282`)

- Fit box: `galleryThumbMaxW=200`, `galleryThumbMaxH=150` (`thumbnail.go:30-31`). `fitInsideBoxDims` preserves aspect ratio, upscales small images, min 1 per axis (`thumbnail.go:157`). Scale with `draw.ApproxBiLinear` from `golang.org/x/image/draw` into a 200x150 RGBA canvas sub-view. Encode with `image/jpeg` default options (quality 75).
- MD5: over the full snapshot including trailers, lowercase hex via `fmt.Sprintf("%x")` (`thumbnail.go:270`). Valid=true.
- pHash (new in v2): `phash.NewFromImage(src, 32, phash.Options{})` then `PHash(phash.Options{Geometry: "64", Method: "average"})`, `BitLen()==64` required, `Uint64()`, stored as `int64(bits)` Valid=true (`hash_writer.go:10-23`, module `github.com/lbe/go-image-phash v0.2.0`). The input is the decoded source pixels (not the thumbnail, not the file). For JPEG the source pixels are the DCT-scaled image, so the hash depends on `chooseJPEGDCTSize` (inference from code; the docs do not say this). All 64 bits survive; 0 is a valid hash and differs from NULL.
- pHash error: `slog.Error("GenerateThumbnailAndHashes source pHash", "err", err)` and a valid 0 is stored; the file still succeeds (`thumbnail.go:273-279`). Dev had the same best-effort behavior with `imagehash.NewPHash64` over a 64x64 squash of the thumbnail. Hashes differ completely between dev and v2.
- JPEG encode error or MD5 copy error: returns the error and puts the pooled buffer back (`thumbnail.go:250-266`).

### 1.4 Source read and memory budgets (`workspace.go`, all constants quoted)

Constants (`workspace.go:22-30`): `sourceRetainCap = 8 << 20` (8 MiB), `rgbaRetainCap = 16 << 20` (16 MiB), `workspaceBudgetCap = 256 << 20` (256 MiB), `sourceReadChunk = 32 << 10` (32 KiB), `sourceInflightCap = 192 << 20` (192 MiB). `wuffsDecoderBytes = 128 << 20` (`wuffs_decode.go:17`). `galleryCanvasBytes = 200*150*4 = 120000`. `maxJPEGComponents = 4`, `jpegBlockCoeffBytes = 256` (`jpeg_header.go:7,10`).

Behavior that must be kept (this is the answer to "what does `workspace.go` do that matters"):

1. **Worker-owned reusable scratch.** One `Workspace` per discovery worker (`service.go:230`, created by `NewWorkerProcessor`) and one per call for direct calls (`service.go:155`, `processor.go:53`). Reuse across files avoids allocation: a source buffer up to 8 MiB, a 120000-byte gallery canvas, and for PNG/GIF a decode buffer such that decode + canvas fit in 16 MiB. Content is cleared before reuse (`clear(pixels)`, `clear(dst.Pix)` for GIF). Encoded output never aliases workspace storage (`workspace.go:81`); the output is a pooled `*bytes.Buffer` handed to the writer.
2. **Process-wide retention cap, non-blocking.** Retained capacity (`cap(source)+cap(rgba)+cap(decode)`) across all workspaces is charged against one 256 MiB budget (`workspace.go:32-48,386`). When the charge fails, the work uses a temporary array that is dropped at `ResetFile`; it never waits for credit. With at most 8+16 MiB retained per workspace this only binds above ~10 workers (inference, arithmetic). See open question Q1.
3. **One process-wide oversized slot, context-aware.** A capacity-1 channel (`workspace.go:50-71`). Taken (once per file, reentrant per workspace, `acquireOversized` `workspace.go:112`) by: source backing above 8 MiB (`workspace.go:151`); a JPEG whose decode estimate exceeds 16 MiB (`workspace.go:296`); PNG/GIF where `size + 120000 > 16 MiB` (`wuffs_decode.go:93-98`). Released at `ResetFile`. Ordinary work never waits on it. Acquire returns `ctx.Err()` on cancellation and gives the slot back if cancellation raced with acquisition.
4. **192 MiB in-flight source cap**, `semaphore.Weighted` (`workspace.go:75`). One all-or-nothing acquire per file in `ReadSource` before any reading, weight `min(max(sizeHint, 32 KiB), 192 MiB)` (`workspace.go:125`): files at or above 192 MiB take the whole cap and read alone. Released at `ResetFile` or `Close`. Growth beyond the hint (file changed after the walk) is not charged again. Blocks until available or ctx is cancelled; cancellation leaves no charge. Covers temporary buffers that the 256 MiB retention budget does not.
5. **Pre-size from hint.** If hint > 0 and <= 192 MiB the buffer is allocated at the hint up front; a hint above 8 MiB takes the oversized slot (`workspace.go:171`). Larger hints never allocate eagerly. Otherwise growth doubles, capped at 8 MiB while the need is <= 8 MiB (`workspace.go:194-205`).
6. **Decode estimate** (`estimateDecodeBytes`, `workspace.go:231`): RGBA bytes `w*h*4` after the JPEG DCT scale `((w*dct+7)/8) x ((h*dct+7)/8)`, plus for progressive JPEG the coefficient storage that go-scaled-jpeg keeps: per component `mcusX*H*mcusY*V` blocks times 256 bytes (`jpeg_header.go:97-113`; `parseJPEGFrame` reads SOF for sampling factors; `jpeg_header.go:23-92`). Invalid dimensions return `invalid decode dimensions WxH`. Progressive overflow returns `invalid progressive JPEG dimensions WxH`.
7. **Decoder lifecycle.** The Wuffs decoder is created lazily on first PNG/GIF, kept for the worker's later files, and released at `ResetFile` only when `decoderReleasePending` (set by: source capacity > 8 MiB, decode surface > 16 MiB, any PNG/GIF decode error), and always at `Close` (`workspace.go:360-402`, `wuffs_decode.go:56-70`). Each live production decoder calls `memlimit.Reserve(128 MiB)` and `memlimit.Release` on drop. Guest memory is reclaimed by GC after the reference is dropped (`wuffs_decode.go:38`).
8. **Wuffs checks before allocation** (`wuffsLayout`, `wuffs_decode.go:45`): `Meta.Err==0`, format matches, width/height non-zero, `stride == width*4`, `width*4*height <= MaxUint32`, plus an int overflow guard. `Reserve(0, len(src))`, then `Probe`, then `Reserve(size, len(src))` before `DecodeRGBA`/`DecodeFrame`. Source reservation precedes Probe; oversized admission precedes destination reservation.
9. **Cancellation.** `ctx.Err()` checked at entry, between decoder stages, between source read chunks, and before returning; a cancelled result releases the output buffers (`workspace.go:326-331`). Cancelled input is not classified as corrupt (the error is `context.Canceled`/`DeadlineExceeded`). Active Wuffs calls finish cooperatively (not interruptible).
10. **Read errors.** 100 consecutive zero-byte reads with nil error return `io.ErrNoProgress`; non-EOF read error is returned; EOF ends (`workspace.go:213-224`).
11. **Close is idempotent**; later `ReadSource`/`Generate` return `thumbnail workspace closed`. `Generate` before `ReadSource` returns `thumbnail workspace has no source snapshot`.
12. **Not charged**: guest/Wuffs memory, JPEG encoder output, database memory (`ARCHITECTURE.md:989`).

Not behavior (R21 evidence or seam code, no v3 equivalent): `WorkspaceStats`/`Stats()` (`workspace.go:79,405`), `snapshot()` (`workspace.go:408`, unreachable per deadcode), `testSeams.NewDecoder`, the `wuffsDecoder` interface and `wuffsSession` wrapper (`wuffs_decode.go:19-39`), `productionWorkspaceBudget`, `productionOversizedAdmission`, `productionSourceInflight` globals (`workspace.go:73-75`), the `newWorkspaceWithBudget`/`newWorkspaceWithInflight` chain (`workspace.go:106-111`), `inflightLimit` field kept for tests, the `n<0||n>len(chunk)` and `len(buf) > MaxInt-n` checks (cannot occur, R20), the per-file `tempSource`/`tempRGBA`/`tempCanvas` machinery (it exists to express "temporary arena when the budget refuses"; the behavior needed is "allocate fresh and drop at ResetFile").

### 1.6 memlimit (`internal/memlimit`, all new)

Called once from `SubsystemManager.Start`: `maxWorkers = memlimit.Apply(maxWorkers, metadata.PoolSize())` (`internal/server/subsystem_manager.go:183`), after config and `DefaultMaxWorkers` resolution, before the pool is built. The return value is the effective worker count.

- RAM (`ram_linux.go`): smaller of `/proc/meminfo` `MemTotal` and cgroup v2 `/sys/fs/cgroup/memory.max` (numeric only; `max` or error ignored). Darwin `sysctl hw.memsize`; Windows `GlobalMemoryStatusEx` `TotalPhys`; other platforms 0 (unknown).
- Ceiling = `ram*75/100`; 0 if RAM unknown (`memlimit.go:130`).
- `floor(workers, servers) = 20 MiB + workers*13 MiB + servers*64 MiB + 256 MiB` (`memlimit.go:121`); `limit = floor + headroom (96 MiB)`. The 256 MiB duplicates `workspaceBudgetCap` (comment at `memlimit.go:18-20`: duplicated because thumbnail imports memlimit).
- `compute`: if RAM is 0 or `limit <= ceiling`: `(limit, workers, "computed")`; else recompute with 1 worker: if it fits `(limit,1,"workers_reduced")`; else `(ceiling, 1, "capped")` (`memlimit.go:105-116`).
- `GOMEMLIMIT` set (any value): no limit set, no GC change, returns `workers` unchanged; logs `Info "memory limit" limit_source=env limit=<current> ram ceiling workers exiftool_servers` once (`memlimit.go:48-54`).
- Otherwise, once per process (`sync.Once`): `debug.SetMemoryLimit(min(base+reserved, ceiling))`; unless `GOGC` is set, `debug.SetGCPercent(-1)` (gc="off"), else gc="env". Logs `"memory limit"` with `limit_source` (`computed|workers_reduced|capped`), `limit`, `gc`, `ram`, `ceiling`, `workers`, `exiftool_servers`; level Warn for `workers_reduced` and `capped`, Info otherwise (`memlimit.go:57-74`). Later calls recompute and return an effective worker count but do not change the limit (first call wins; the return value can disagree with the applied limit if arguments differ, inference).
- `Reserve(n)`/`Release(n)` adjust a reserved sum under a mutex; while a computed limit is active the runtime limit becomes `min(base+reserved, ceiling)` again. With `GOMEMLIMIT` set, or before Apply, they only accumulate (`TestReserveBeforeApplyCountsOnApply`). Only user: thumbnail Wuffs decoder, 128 MiB per live decoder (`wuffs_decode.go:61`).
- The only production behavior documented to operators: `README.md:541`, `DEPLOYMENT.md:29`, `ARCHITECTURE.md:803`.

Constants to preserve: GC percent -1 when computed; 75% ceiling; 20/13/64/256/96 MiB; 128 MiB per decoder; log message text `memory limit` and its keys.

### 1.7 Hash cutover (`internal/server/database/hash_cutover.go`, migration 024)

- Migration 024 up: `UPDATE files SET phash = NULL WHERE phash IS NOT NULL;` down: `SELECT 1;` (cannot restore). Main schema becomes 24 (dev latest is 023).
- `migrateMainWithCutover` (`hash_cutover.go:12-60`), called from `migrateDB` (`app.go:166`): reads `schema_migrations` through the temp `*sql.DB`: accepts zero rows or one row with integer version >= 0 and integer dirty 0 or 1 (checked with `typeof()`); multiple rows, NULL, wrong types, scan/iterate/close errors, or dirty=1 fail startup before any removal. If there are zero rows or version < 24, `os.RemoveAll(<dir of DB>/<DB base name>-dque)` runs (the write-overflow dque; a missing directory succeeds); a removal error fails startup. Then `m.Up()`; `ErrNoChange` returns `(false, nil)`; other error `up migration failed: %w`. Queued file, cache and folder-index writes in that overflow are lost deliberately (`image-stack-v2-hash.md`).
- No backfill: unchanged files keep NULL phash because the mtime/size/MD5 skip decision is unchanged.
- `app.go:149` also changes the temp connection driver from `sql.Open("sqlite3", ...)` to `sql.Open("sqlite", ...)` (modernc, already blank-imported at `app.go:17`) with the stated reason "reproduced WAL reopen failures when two drivers coexist; exact mechanism not established" (`image-stack-v2-hash.md`). ## 2. Intended changes versus dev

Approved:

- **New pHash**: `hash_writer.go`, `thumbnail.go:273`, migration 024, `hash_cutover.go`, go.mod `github.com/lbe/go-image-phash v0.2.0`. Algorithm in 1.3. Removal of `evanoberholster/imagemeta/imagehash` use, the 64x64 canvas pool (`phashRGBAPool`, `acquirePHashRGBA`) and the local `imagemeta` replace (go.mod).
- **Wuffs decoding**: `wuffs_decode.go`, `workspace.go` decode branch, `memlimit.Reserve(128 MiB)` per decoder, go.mod `github.com/lbe/wuffs-wasm v0.4.0` (+ `lbe/cfsread`, `lbe/wasm2go-wasi-host` indirect). PNG/GIF only.
- **Malformed JPEG fails in decode**: marker pre-filter removed; `Generate` has no marker check. (The filter itself, `ValidateJpegMarkers` and `HasValidJpegMarkers`, lives in `files/metadata.go`, other component.)
- ExifTool/IPTC: not in this component (`go-exiftool-wasm` is a metadata dependency).

Other behavior changes versus dev, "unapproved change: needs a decision":

1. **Unapproved change: single-read workspace and in-flight/retention/oversized budgets.** Dev opened the file repeatedly with no memory admission. v2 adds the 192 MiB in-flight cap, the 256 MiB retention budget and the 1-slot oversized admission. These bound memory and may delay files (a >=192 MiB file reads alone; oversized work serializes). R4 does not list them.
2. **Unapproved change: process-wide GC policy.** `memlimit.Apply` sets a soft memory limit and `SetGCPercent(-1)` unless `GOGC` is set; workers can be reduced (to 1). Dev set no limit. Affects every deployment; documented in README and DEPLOYMENT.
3. **Unapproved change: write-overflow discard on cutover.** Pre-24 startup deletes `<db>-dque` (loses queued writes). Needed to avoid old-hash writes after clearing, but not in the R4 list.
4. **Unapproved change: migrator temp driver `sqlite3` to `sqlite`** (`app.go:149`). Reason is empirical, not understood.
5. **Unapproved change: pHash is of source pixels at the JPEG DCT scale**; two sizes of one image can hash differently (inference).
6. **Unapproved change: PNG/GIF pixels** differ from stdlib decode (premultiplied 8-bit RGBA, GIF frame 0 at frame bounds). Thumbnails may differ byte-wise from dev for PNG/GIF (the "pixel-equal" claims live in `wuffs_decode_test.go`; I did not verify them). Part of "Wuffs decoding" if the user accepts that.
7. **Unapproved change: pHash failure persists valid 0** (same as dev; listed so v3 keeps it).

## 5. Boundary notes

`go list` on v2:

- `internal/thumbnail` imports: `internal/gensyncpool`, `internal/memlimit`, `lbe/wuffs-wasm`, `lbe/go-image-phash/phash`, `m8rge/go-scaled-jpeg`, `x/image/{draw,webp}`, `x/sync/semaphore`, stdlib. Imported by: `internal/discovery`, `internal/server/database/storage`, `internal/server/files`. It does not import database packages, but its API uses `database/sql` types (R16; `depguard` covers `thumbnail`).
- `internal/memlimit` imports stdlib only (+ `x/sys` on darwin/windows). Imported by: `internal/server` (`subsystem_manager.go:183`) and `internal/thumbnail`.
- `internal/gensyncpool` imports `sync`. Imported by cachelite, dque, parallelwalkdir, cachepreload, ui, storagepayload, thumbnail.

Proposals (need user approval):

1. **memlimit stays a package** (R1/R11): it exists for a real reason (process-wide GC policy plus a reservation API that another package calls). It is not an import-cycle shim. But the duplicated 256 MiB (`memlimit.go:20`) is a symptom: memlimit should receive the retained-scratch estimate as an argument to `Apply` (or thumbnail exports `RetainedBytes`) instead of mirroring a constant. Choose one owner of the budget numbers.
2. **Workspace should live in `thumbnail` but split by responsibility, not by file count**: source reading and admission (`ReadSource`, in-flight cap, oversized slot) have nothing to do with image decoding. One option is to keep them in `thumbnail` as one small `scratch` type (one file) with `semaphore.Weighted` for in-flight and the oversized slot; no new package.
3. **Wuffs decoder reuse**: if `wuffs.Decoder` can be used directly with a nil-able pointer, drop the interface and wrapper (R8).
4. **`files/thumbnail.go`**: remove; callers use `storage` (the storage component owns thumbnail upserts and `WriteFileInTx`).
5. **`hash_writer.go`** into `thumbnail.go` or rename `phash.go`.
6. **`hash_cutover.go`** belongs with the migration code in `internal/server/database`; one function called by `migrateDB`; no package change.
7. Do not recreate `Get*`/`Put*` null-pool wrappers: `Generate` should return `(thumb *bytes.Buffer, md5 string, phash int64, err error)` and the files package should create `sql.Null*` (R16). Open: sync.Pool for `*bytes.Buffer` thumbnail output is a measured v2 behavior (R25); keep it, but only that one pool plus the MD5 hasher if benchmarks show a win (I did not measure).

## 6. Open questions (recommended answers)

- Q1. Keep the 256 MiB retention budget across workers? It binds only above about 10 workers (arithmetic from 8+16 MiB per workspace), and `memlimit` depends on the number. Recommend: keep the cap but implement it simply (an `atomic.Int64` charge, non-blocking fallback to fresh allocation) and pass the number to memlimit from one owner. Dropping it saves about 40 lines but changes memory on many-core hosts (R4 risk).
- Q2. Keep `GenerateThumbnailAndHashes` (io.ReadSeeker path)? It is unreachable in production on v2. Recommend: remove it; test through `Workspace`. It has more tests than any production path, which is R26.
- Q3. Cap or retain the Wuffs decoder across files? v2 retains it per worker and releases on error/oversize. Recommend: keep (reuse is the measured benefit; docs `image-stack-v2-dec.md`), and drop the pending-flag by releasing the decoder at `ResetFile` whenever the previous file errored or was oversized, recorded as one field on the workspace.
- Q4. `sql.Open("sqlite")` vs `"sqlite3"` in `migrateDB`: recommend accepting the v2 change (it fixed reproduced failures) but add a one-line comment with the evidence reference; confirm with the user because it is an unexplained fix.
- Q5. Does the user accept that pHash depends on DCT scale for JPEG (Section 2 item 5)? Recommend: accept, it was already v2's accepted behavior and avoids a full-resolution decode.
- Q6. Cutover scope: accept discard of `<db>-dque` on first v3 start from pre-24? Recommend: yes (otherwise old-hash writes resurrect after migration), and document it in DEPLOYMENT.md.
- Q7. Should `gensyncpool` comment-only edits be carried? Recommend: no (R6 minimal diff vs dev).
- Q8. `memlimit.Apply` returning the worker count conflates limit-setting and worker policy (R17). Recommend keep for now (one call site, effective worker reduction depends on the computed floor), but state it in the doc comment.
